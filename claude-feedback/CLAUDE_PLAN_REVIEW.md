## 결론

전체 방향과 1단계 경계 확장은 타당하다. 다만 최초 검토 시점의 계획 그대로
`data:metrics` 단계로 진행하면 경기 120개 동에 서울 캐시·결측치·0값이 섞여 잘못된
등급이 생성될 수 있었다.

다음 3개 P0 항목이 후속 구현에 반드시 반영되어야 한다.

1. 서울 전용 Sbiz·OSM 캐시의 범위 검증 및 무효화
2. 경기 치안 결측 시 `4-score.mjs`가 재가중한다는 잘못된 가정 수정
3. 지표별 지역 단위 완전성 검증 추가

경계 커밋 자체는 확인 결과 정상이다.

- 총 34개 구이며 처인구는 포함되지 않았다.

  - 경도: `126.76469 ~ 127.19596`

## P0-1. Sbiz·OSM 캐시가 자동으로 확장된다는 설명은 틀림

계획서 58~61행은 경계만 확장하면 소상공인 데이터가 자동으로 따라온다고 설명하지만,
최초 검토 시점의 코드는 기존 캐시가 있으면 요청한 구 코드를 검사하지 않고 즉시 반환했다.

- OSM: `scripts/3-metrics.mjs:374`
- Sbiz: `scripts/3-metrics.mjs:562`

검토 당시 캐시 상태:

- `sbiz-seoul.json`: 554,092개, 25개 구, 좌표 전부 서울 범위
- `osm-poi.json`: 47,446개, `37.41` 이남 데이터 0개

이 상태로 실행하면 경기 동들은 다음처럼 계산된다.

- 편의점·음식점·의료시설: 0 → 편의 점수 하락
- 유흥업소: 0 → 치안 점수 상승
- 버스 정류장: 0 → 편의 점수 하락

단순히 캐시를 한 번 지우는 작업만 문서화할 것이 아니라 캐시 자체를 범위 인식 구조로
변경하는 것이 안전하다.

권장 수정:

- `sbiz-seoul.json`을 범위 중립 이름으로 변경
- Sbiz 캐시에 정렬된 `guCodes`, 스키마 버전 저장
- OSM 캐시에 `bbox`, 스키마 버전 저장
- 요청 범위와 캐시 메타데이터가 다르면 자동 거부·재수집
- 34개 구가 캐시에 모두 존재하는지 검증
- 경기 3개 시의 Sbiz·버스 정류장 배정 건수가 각각 0보다 큰지 검증

## P0-2. 경기 치안 결측 시 재가중된다는 설명은 사실이 아님

계획서 176~179행은 경기 `crimePer1k`를 `null`로 두면 가중치가 재분배된다고 하지만
최초 검토 시점의 실제 동작은 달랐다.

`scripts/4-score.mjs:94`는 전체 동의 50% 이상 값이 존재하면 해당 지표를 활성화한다.
서울 427개에 값이 있고 경기 120개가 `null`이면 유효율은 `427/547 = 78%`이므로 치안
지표는 그대로 활성화된다.

이후 결측 동은 `scripts/4-score.mjs:117`에서 재가중되는 것이 아니라 백분위 `50점`을
받는다.

따라서 다음 중 하나를 명시적으로 선택해야 한다.

- 경찰 관할과 인구 분모를 일치시키는 근거 있는 변환
- 수원·용인 등을 시 단위로 집계하고 시 단위 지표임을 표시
- 비교 가능한 자료가 없으면 이번 확장에서는 `crimePer1k`를 전체 지역에서 제외

경기만 `null`로 두는 방식은 사용하면 안 된다. 특히 경찰서 3개를 수원 4개 구에 임의
배분하거나 경찰서 2개를 용인 3개 구에 임의 배분해서도 안 된다.

## P0-3. 지역별 완전성 검증이 필요함

최초 검토 시점의 `metrics.available`은 전역 상태만 봤다.
관련 코드는 `scripts/3-metrics.mjs:269`이다.

그래서 다음 오류가 발생해도 파이프라인이 성공할 수 있었다.

- 서울 전용 교통사고 CSV를 그대로 쓰면 경기 동은 사고 0건으로 계산되고 오히려 가장 안전하게 평가됨
- 경기 월세 API 요청이 전부 실패해도 서울 표본만 있으면 파이프라인은 계속 진행됨
- 경기 범죄가 전부 `null`이어도 중립 50점으로 계산됨
- 오래된 Sbiz·OSM 캐시를 쓰면 경기 데이터가 0이지만 지표는 사용 가능으로 표시됨

데이터 생성 후 다음 표를 시·구별로 출력하고 예상 범위를 벗어나면 실패하도록 해야 한다.

- 행정동 수
- Sbiz 전체 업소 및 업종별 배정 수
- OSM 버스 정류장 수
- 범죄 값 존재 동 수
- 교통사고 지점·사고건수·0인 동 비율
- 월세 API 성공/실패 요청 수
- 월세 표본 수·직접 매칭 수·구 중앙값 대체 수
- 지표별 `null` 비율과 0 비율

단순히 “결측률 확인”이 아니라, 경기 지역 전체가 0 또는 `null`이면 빌드를 중단하는
검증이어야 한다.

## P1-1. “통근 엔진은 손댈 필요 없음”은 과한 결론

그래프에 신분당선은 있지만 현재 통근 계산은 동 대표점 반경 1.5km 안에 역이 있어야 한다.

- 기준: `src/lib/constants.ts:55`
- 적용: `src/lib/commute.ts:115`

현재 대표점으로 실측하면 추가된 120개 동 중 47개, 즉 39.2%는 출발 후보역이 하나도 없다.

| 지역 | 추가 동 | 1.5km 밖 |
|---|---:|---:|
| 성남 | 50 | 16 |
| 수원 | 44 | 17 |
| 용인 기흥·수지 | 26 | 14 |
| 합계 | 120 | 47 |

특히 핵심 대상인 `용인시 수지구 동천동`의 대표점은 동천역에서 약 4.0km 떨어져 있어
현재 모델에서는 동천역이 있는 동천동 자체가 통근 불가로 나온다.

또한 처인구 제외 근거로 “에버라인이 없어서 전부 회색”을 들었지만, 포함된 기흥구도
15개 동 중 10개가 후보역 없이 회색이다.

이번 작업에서 반드시 에버라인이나 대표점 모델을 고쳐야 한다는 뜻은 아니지만, 다음 중
하나는 결정해야 한다.

- 대표점 모델을 보강
- 에버라인 추가
- 현재 한계를 수용하되 47개 동 목록과 핵심 시나리오 결과를 검증·공개

현재 상태를 “엔진 변경 불필요”라고 확정하면 안 된다.

## P1-2. OSM·지도 범위가 너무 좁게 제시됨

계획서는 남쪽 범위를 광교 `37.30` 정도로 설명하지만 실제 포함 경계는 `37.21564`까지
내려간다.

따라서 OSM BBOX와 지도 `maxBounds`는 최소 `37.20` 부근까지 포함하거나, 가능하면
대상 GeoJSON의 실제 bounds에 여백을 더해 산출해야 한다.

최초 검토 시점의 지도 남쪽 제한은 `37.34`였다. 관련 코드는
`src/components/MapView.tsx:58`이다.

고정 숫자를 사용할 경우 검증 기준은 “광교역이 보이는가”가 아니라 “547개 동의 전체
geometry가 bounds 안에 있는가”가 되어야 한다.

여부도 확인한다.

## P1-4. 교통사고 데이터의 기간·유형을 동일하게 맞춰야 함

기존 서울 CSV는 2012~2024년 누적이며 다음 4개 유형만 사용한다.

- 스쿨존 어린이
- 보행 어린이
- 보행 노인
- 자전거

전국 최신 파일에서 경기만 필터링할 때도 서울과 동일한 연도와 유형을 사용해야 한다.
최신 연도만 추가하거나 경기만 다른 기간을 사용하면 통합 상대평가가 성립하지 않는다.

지역별 `사고연도 × 사고유형` 건수를 출력해 서울과 경기의 범위가 같은지 검증해야 한다.

## 검토 범위

최초 검토는 계획서, 당시 코드, 생성된 데이터 산출물과 공식 데이터 페이지를 대상으로 한
