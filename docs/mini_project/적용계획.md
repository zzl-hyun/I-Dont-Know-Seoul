# Mini-project 적용 계획 — "I Don't Know Seoul"을 과제 산출물로

과제(SKALA Mini-project ①)는 **코드가 아니라 설계 문서의 논리적 일관성**을 봅니다.
구현물은 제출 대상이 아니고, 채점은 산출물 5개(개요.pdf · API.yml · API.pdf · DB.dbml · DB.pdf)로만 합니다.

## 1. 결론

적용 **가능합니다.** 오히려 유리한 조건이 세 가지 있습니다.

- 서비스 개요·배경(30점 항목)이 이미 `docs/`에 실측 근거로 다 적혀 있습니다. 보통은 이 부분을 지어내는데, 우리는 "왜 이 지표인가"를 데이터로 답할 수 있습니다.
- 화면이 실제로 돌아갑니다. 와이어프레임을 상상으로 그리지 않고 **실행 화면을 캡처해 박스·번호만 얹으면** 됩니다("그림은 반드시 개요 PDF 안에 이미지로" 요건 충족).
- 창의/독창성은 채점 대상이 아니라(창의·독창성 X), 주제가 특이해서 손해 볼 일이 없습니다.

단, **있는 그대로 내면 시스템 설계 40점에서 크게 깎입니다.** 이유는 아래 갭입니다.

## 2. 갭 — 현 구조가 채점표와 어긋나는 지점

| 과제 요구 | 현재 프로젝트 | 조치 |
|---|---|---|
| 데이터 모델 20점 (PK/FK, 1:N, M:N, 정규화) | **DB가 없음.** KV에 JSON 번들 1개 + 클라이언트 계산 | 같은 서비스를 RDB로 정규화한 **설계상의 v2**를 그린다 (테이블 11개) |
| API 명세 20점 (화면별 호출 API 전체) | 엔드포인트 **2개** (`/api/data`, `/api/geocode`) | 화면 단위로 쪼갠 REST API 16개로 재설계 (조회는 전부 GET) |
| 액터별 기능 정의 | 액터가 사실상 1명(익명 게스트) | 게스트 / 회원 2액터 (후기 쓰기에서만 갈라짐) |
| 예외처리 400·401·403·404·409·500 | 401·409가 나올 상황 자체가 없음 | 후기 기능에서 자연히 성립(미로그인 401, 동당 1건 409) |
| UI 데이터 ↔ ERD ↔ API 3자 일치 | 번들 JSON 구조라 테이블 대응이 없음 | `draft/` 세 문서로 ID를 물린다 |

핵심 판단: **"현재 배포된 구조를 문서화"가 아니라 "이 서비스를 서버 기반으로 만든다면"으로 문서를 씁니다.**
지문이 요구하는 건 구현 일치가 아니라 설계 일관성이고, 감점 문구도 "UI 데이터가 ERD에 없음 / API와 데이터 모델 불일치"뿐입니다.
반대로 범위를 키우는 건 감점(과도하게 큰 범위)이므로 화면은 **지금 있는 것 + 후기**까지만 넓힙니다. 운영자용 백오피스는 만들지 않습니다 — 지표 갱신은 배치가, 신고 후기는 누적 3건 자동 숨김 정책이 처리합니다.

## 3. 확정한 범위 — 로그인은 후기에만

무로그인 기조를 유지합니다. 목적지 검색·등급 지도·동 상세·추천·공유는 **전부 계정 없이** 씁니다.
로그인이 필요한 지점은 **하나**입니다 — 목적지를 정한 뒤 "그 동네에 실제로 살면서 여기로 출퇴근해 본 사람"의 후기를 **남길 때**.
읽기는 비로그인, 쓰기(작성·수정·삭제·도움돼요·신고)만 로그인입니다.

이 선택이 과제 채점에 맞는 이유:

- 401(미로그인 쓰기) · 403(남의 후기 수정) · 409(한 동에 후기 2건, 도움돼요 중복)이 **억지 없이** 생깁니다.
- `users × reviews`(1:N), `review_helpfuls`(M:N), `reviews → destinations`(통근 목적지 참조)로 관계 다양성이 확보됩니다.
- 후기가 "목적지 기준 추천"과 물려서, 기존 자동 지표와 **다른 축의 정보**가 됩니다.

주의 — **후기는 등급 산정에 절대 넣지 않습니다.** `CLAUDE.md`의 확정 결정("평판 산정은 공공데이터 자동 지표, 사용자 리뷰는 탈락")과 충돌하지 않게, 후기는 등급과 분리된 "실사용 후기" 레이어로만 설계합니다. 문서에도 그렇게 명시합니다.

## 5. 남은 수작업 (사람이 해야 하는 것)

1. **와이어프레임 캡처** — `npm run cf:dev` 로 띄운 실제 화면을 캡처해 ①②③ 번호를 얹습니다. 필요한 컷은 `draft/화면설계서.md` 의 각 화면 ② 영역에 `[캡처: ...]` 로 표시해 뒀습니다.
2. **PDF 변환** — md → 워드/한글 붙여넣기 → PDF. yml·dbml은 각각 Swagger Editor·dbdiagram.io에 붙여 PDF를 한 벌 더 뽑습니다.
3. **파일명 치환** — `{코드}`, `{이름}`, `{프로젝트명}` 확정 후 일괄 치환.

## 6. 분량 — 3일 과정에 맞춘 슬림화 (2026-09-15 조정)

이미 굴러가는 서비스를 알고 쓰다 보니 초안이 교안 샘플의 2~3배로 불었고, 다시 줄였습니다.

| | 교안 샘플 | 1차 초안 | 현재 |
|---|---|---|---|
| 화면 | 6 | 12 | 9 |
| 테이블 | 6 | 18 | **11** |
| API operation | 약 10 | 28 | **16** |
| 기능 요구사항 | 12 | 25 | **16** |
| 비기능 | 4 | 8 | **6** |

줄이면서 함께 고친 것:

- **인증은 소셜 로그인으로** — 자체 가입 폼(이메일·비밀번호·확인)을 없애고 카카오·GitHub OAuth만 둡니다. 회원가입 화면 하나가 통째로 사라지고, 401·403·409는 그대로 살아 있습니다. 과제가 "Security Schemes 제외"라고 했으므로 `securitySchemes` 블록은 쓰지 않고 인가·콜백 엔드포인트 2개로만 표현합니다.
- **조회 API를 전부 GET으로** — `POST /commutes`·`POST /rankings` 를 `GET /regions`·`GET /regions/{code}/commute` 로 바꿨습니다. 실습안내 체크리스트에 "조회=GET"이 명시돼 있습니다.
- **429 제거** — 과제가 정한 코드 집합(400·401·403·404·409·500) 밖이라 뺐습니다.
- **테마 전환 제거** — "기능이 문제 해결과 연결되지 않음"은 세부 평가표의 첫 감점 항목입니다.
- **읽기 전용 테이블 정리** — 스냅샷 버전 관리(`snapshots`), 백분위 분리 테이블, 주택유형별 월세 표, 역 접근 프로필, 공유 링크 저장을 걷어내고 그 값들을 컬럼·쿼리스트링으로 흡수했습니다.

## 7. 의도적으로 뺀 것

- **서비스 관리자 액터와 백오피스 화면** — 무로그인 서비스에 운영 화면을 붙이면 화면 수만 늘고 "과도하게 큰 범위" 감점 위험이 커집니다. 대신 지표 갱신은 오프라인 배치(스냅샷 적재 → 게시본 교체)로, 신고 후기는 누적 3건 자동 숨김으로 설계해 사람이 개입하는 지점을 없앴습니다.
- **즐겨찾기·저장한 검색** — 로그인을 유발하므로 뺐습니다. 조건 공유는 화면이 만드는 URL 쿼리스트링이 대신합니다(서버 저장 없음).
- **후기 신고·제재** — 운영 주체가 없는 설계라 기능째 뺐습니다.
- **통근시간 감쇠 함수 Φ(t) · 주택유형별 월세 환산 · 지표 스냅샷 롤백** — 설명 부담이 커서 문서에서는 빼고, 요구사항정의서 2-5에 "다음 단계로 미룸"으로 명시했습니다. 발표 마지막 "다음 개발 시 고려사항" 슬라이드에서 말할 재료로 씁니다.
